How Real Compilers Enforce Local Variables (and How to Start Small)
You're asking exactly the right question. Let me demystify what real compilers do, then give you a path that works for your SML.

The Big Picture: What Real Compilers Do
Real compilers enforce local variables through three coordinated mechanisms:

1. Scope Analysis (Compile Time)
The compiler builds a tree of scopes as it parses:

Global Scope
├── fn main
│   ├── local x        ← "x" refers to this x
│   └── if block
│       └── local y
└── fn add
    └── local a, b     ← "a" and "b" are local to add
When you see fn add(), push a new scope. When you see }., pop it. Every variable declaration is added to the current scope. Every variable reference is resolved by walking the scope chain from innermost to outermost.

2. Allocation Decision (Compile Time)
After scope analysis, the compiler knows for each variable:

Global variable → lives in static memory (a fixed address, alive for the whole program)
Local variable → lives on the stack (address is frame_pointer + offset, alive only during the call)
Parameter → passed by caller, also at frame_pointer + offset
3. Stack Frame (Runtime)
When a function is called, a frame is pushed onto the call stack:

┌─────────────────────┐
│ Return address      │  ← saved by CALL instruction
├─────────────────────┤
│ Saved frame pointer │  ← for restoring caller's frame
├─────────────────────┤
│ Parameter 1         │  ← at +offset from FP
│ Parameter 2         │
├─────────────────────┤  ← Frame Pointer points here
│ Local variable 1    │  ← at -offset from FP
│ Local variable 2    │
└─────────────────────┘
Locals are at fixed offsets from the frame pointer, known at compile time. No allocation happens at runtime — just pointer manipulation.

Your Specific Confusion: "What is 'the variable used inside fn'?"
You're conflating scope analysis with allocation. Let me untangle this.

A compiler doesn't "decide at runtime" whether something is local. It decides at compile time during semantic analysis, by tracking which scope each variable belongs to.

Here's the thing you got right intuitively: if a variable is never referenced outside a function, it can be allocated locally (on the stack). If it IS referenced outside, it must be global (so both the function and the outside code see the same memory).

But the compiler doesn't "check at runtime." It walks the AST twice:

Pass 1: Build the symbol table with scopes. For every reference, mark whether it's used only inside the function or also outside.
Pass 2: Generate code using the symbol table's decisions.
A Simple Path Forward for Your Compiler
Since you want to "start small" with int/float/double and your SML is very simple, here are three options in increasing complexity. Pick one and stick with it.

Option A: Everything is Global (Simplest — Start Here)
Just treat all variables as global. Function parameters are passed by storing their values into known global locations before the call.

Compiler generates:
  for "call add(3, 5)":
    load 3 into known_slot_0    ; parameter passing
    load 5 into known_slot_1
    call add
    read result from known_slot_2

  for "fn add() {":
    ; reads known_slot_0 and known_slot_1 as its parameters
    ; writes to known_slot_2 as its return value
Pros: Trivial. No stack frame for variables.
Cons: No recursion. Reentrancy is impossible. Name conflicts if two functions use the same temp.

This is how the original Simpletron and early BASICs worked. It's a perfectly valid starting point.

Option B: Per-Function Static Locals (Medium)
You allocate locals for each function in a dedicated "local area" for that function. Each function has a fixed size computed at compile time.

Memory layout:
  [0..49]   global variables
  [50..79]  fn add's locals
  [80..109] fn sub's locals
  ...
  [130..148] stack for return addresses
Compiler decides: "Variable x is only used inside add, so I'll allocate it in add's local area at offset 3, accessible at absolute address 53."

Pros: No recursion needed. Locals don't pollute the global namespace.
Cons: Still no recursion. Slightly more complex to track.

This is how Fortran I worked (and FORTRAN didn't have recursion for decades).

Option C: True Stack Frames (Hardest — Do Last)
Each function call dynamically allocates space on the stack. The frame pointer points to the current frame. Locals are at negative offsets from FP.

Call add(3, 5):
  push FP onto stack
  FP = SP
  store 3 at FP+3   ; parameter
  store 5 at FP+4   ; parameter
  branch to add

Inside add:
  locals at FP-1, FP-2, ...

Return:
  SP = FP
  pop FP
  branch to saved return address
Pros: Recursion works. Reentrancy works. The "right" way.
Cons: You need real stack management in your SML.

My Recommendation: Start with Option B, Skip to C When You Need Recursion
For your SML, I'd actually do Option B as the next step, not Option A. Here's why:

Your SML already has:

Opcodes 15-18 for stack pointer manipulation
Opcodes 22-23 for indirect addressing
Return address stack at 130-148
You're already 60% of the way to a real stack frame. Just upgrade the symbol table to track scope.

Answering Concern 1 Specifically: Strings and Stack Overflow
"if the statements and data inside fn are much we will run out of stack"

Two separate problems here:

Local variable region overflow: If add has 50 locals, its region needs 50 slots. Just give each function a fixed-size region computed at compile time. Limit locals per function (say 20) and you have a bounded requirement.

String allocation for print: The string "haheehehe" is allocated in the global data region, not the local region. Inside a function, when you say print "hello", the compiler allocates that string literal in the global region because strings need persistent memory. This is exactly what your allocateStringLiteral already does.

The rule is simple: string literals and constants always go in the global region, even when used inside a function. Only variables (let x = ...) become locals.

Answering Concern 4: "Locals are overwritten when called"
This is the recursion problem, and it's the reason Option B is "no recursion." If add calls itself:

fn add(n) {
    if n == 0 return 0
    return add(n-1) + n
}
With Option B, the second call to add overwrites n's slot. Stack corruption.

To get recursion, you need Option C (true stack frames). Here's the upgrade:

Each call to add:
  ┌──────────────────┐ ← old stack pointer
  │  (caller's frame)│
  ├──────────────────┤ ← new stack pointer (frame pointer for add)
  │ saved frame ptr  │
  │ parameter n      │  at +1 from FP
  │ local x          │  at -1 from FP
  │ local y          │  at -2 from FP
  └──────────────────┘
The rule: Before add writes to its locals, it bumps the stack pointer past its locals. When add returns, it restores the pointer. Each call gets a fresh, non-overlapping region.

How to implement on your SML:

// At call site:
PUSH_RETURN_ADDRESS    // existing opcodes 15-18
LOAD arg1 → accumulator
STORE to FP+1          // parameter slot
LOAD arg2 → accumulator
STORE to FP+2
BRANCH to add

// At fn entry:
FP = SP                // mark current stack top as this frame
SP -= numLocals        // reserve space for locals

// At fn exit (}.) :
SP = FP                // pop the locals
FP = saved_FP          // restore caller's frame
BRANCH to [SP]         // return
You'd need two new opcodes:

25 — copy FP to accumulator
26 — set FP from accumulator
But for now, stick with Option B and just say "no recursion." It's a documented limitation. Many real languages started this way (early C, Fortran).

One More Critical Detail: The Lookup Must Be Scope-Aware
Your current lookup() is broken for locals because it returns the first match. With locals, you need:

int lookup(string argument) {
    string name = baseSymbol(argument);
    
    // First: search current scope (locals of current fn)
    for (int i = 0; i < move; i++) {
        if (symbolTable[i].symbol == name && 
            symbolTable[i].scopeName == currentFunctionName) {
            return symbolTable[i].location;
        }
    }
    
    // Then: search global scope
    for (int i = 0; i < move; i++) {
        if (symbolTable[i].symbol == name && 
            symbolTable[i].scopeName == "") {
            return symbolTable[i].location;
        }
    }
    
    return -1;
}
Current scope first, then global. This is the same rule every compiler uses. It's why you can have a local x that shadows a global x.
